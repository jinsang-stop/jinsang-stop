# 인증은 자체 아이디·비밀번호와 서버 세션 쿠키로 한다

상태: accepted

사용자는 직접 가입한 아이디와 비밀번호로 로그인한다. 로그인에 성공하면 Spring 서버가 세션을 만들고 HttpOnly 세션
쿠키를 내려주며, 이후 요청은 이 쿠키로 사용자를 식별한다. 비밀번호는 BCrypt 해시로만 저장한다. 소셜 로그인과
토큰(JWT) 방식은 쓰지 않는다. `공식 카드` 목록·상세와 `강도` 고지는 로그인 없이 볼 수 있고, `훈련 세션`과
그 기록에 닿는 API는 로그인을 요구한다. 미인증 요청은 공통 오류 형식의 401(`UNAUTHORIZED`)로 거절한다.

`훈련 세션`과 `성장 기록`은 계정에 귀속돼야 하므로(ADR-0006) 인증 자체는 필요하다. 소셜 로그인은 가입 마찰이
적지만 외부 앱 등록·키 관리가 필요하고, 시연 장비가 인터넷 없이도 돌아가야 한다는 전제(ADR-0008, ADR-0009)와
어긋난다. JWT는 서버를 여러 대로 늘릴 때 유리하지만 이 제품은 시연 장비 한 대에서 돌고, 프론트가 토큰 저장·갱신·
폐기를 직접 다뤄야 해 로그아웃 하나도 번거로워진다. 우리는 **서버 여러 대로의 수평 확장과 소셜 가입 편의를
포기하는 대신**, 프론트가 `credentials: 'include'`만 켜면 끝나는 단순한 연동과 서버가 세션을 즉시 끊을 수 있는
통제력을 얻는다.

이 결정은 다음을 뜻한다. 세션은 서버 메모리에 있으므로 서버를 재시작하면 모두 로그아웃된다 — 시연 장비 한 대
구성에서는 받아들인다. 프론트(`localhost:5173`)와 백엔드(`localhost:8080`)는 같은 사이트이므로 세션 쿠키를
`SameSite=Lax`로 두고, CORS 허용 출처를 환경변수로 좁히는 것으로 CSRF 방어를 대신해 CSRF 토큰은 쓰지 않는다.
서로 다른 사이트로 배포하게 되면 이 전제가 깨지므로 CSRF 토큰 도입과 함께 이 ADR을 다시 연다.
