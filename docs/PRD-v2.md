## 문제 정의 (Problem Statement)

매장이나 민원 창구에서 일하는 사람은 도발적인 상대를 만나면 그 자리에서 말문이 막힌다. 어떻게 말했어야 했는지는 상황이 끝나고 몇 시간 뒤에야 떠오른다. 이 역량은 겪으면서만 늘지만 현장은 연습장이 아니다 — 실수하면 그 자리에서 손님을 잃거나 본인이 상처를 입고, 같은 상황을 다시 겪을 시점도 고를 수 없다. 응대 매뉴얼과 교육 영상은 무엇을 말해야 하는지는 알려주지만, 상대의 목소리를 들으며 실제로 입으로 말해보는 경험은 주지 않는다. 그래서 자신이 지난주보다 덜 흔들리게 되었는지 확인할 방법도 없다.

## 해결책 (Solution)

사용자는 `시나리오 카드`를 하나 고르고 `강도`를 정한 뒤 `훈련 세션`을 시작한다. 마이크로 말하고 "말하기 끝내기"를 누르면 하나의 `발화 턴`이 닫히고, 카드에 적힌 페르소나대로 연기하는 `민원인`이 음성으로 응답한다. `민원인`은 사용자의 말을 중간에 끊지 않는다 — 턴은 언제나 사용자가 닫는다.

말하는 동안 화면에는 `태도 3축`(정서 안정 · 공감 인정 · 경계 설정) 점수가 발화 턴마다 갱신된다. 이 서비스는 규정상 올바른 조치였는지를 판정하지 않는다. 오직 흔들리지 않았는지, 상대의 감정을 먼저 받아줬는지, 해줄 수 없는 것을 분명히 거절했는지만 본다. `민원인`이 카드의 진정 조건을 충족해 스스로 떠나면 `진정 종료`이고, 그 전에 `하드 턴 상한`에 닿으면 "진정시키지 못한 채 종료"로 기록된다.

세션이 끝나면 리포트가 나온다. 같은 카드·같은 강도로 `진정 종료`에 도달했고 경계 설정 하한선을 넘긴 세션만 `성장 기록`에 쌓이며, 그래프의 주지표는 `소요 턴 수`다 — 같은 상대를 몇 턴 만에 진정시켰는가. `태도 3축`은 "어떤 태도로 거기까지 갔는가"를 설명하는 보조 지표다. 요구를 다 들어주고 빨리 끝내는 경로는 경계 하한선이 막는다.

대사 생성과 채점, 음성 인식과 합성까지 전부 시연 장비 한 대 안에서 돈다. 외부로 나가는 호출이 없어 네트워크 없이도 시연할 수 있고, 사용자가 말한 내용이 장비 밖으로 나가지 않는다. 그 대신 한 번에 한 명만 훈련할 수 있다.

## 사용자 스토리 (User Stories)

1. As a 매장 응대 경험이 적은 알바생, I want 실제 손님이 아닌 상대에게 소리 내어 응대해보고 싶다, so that 처음 겪는 상황을 현장이 아닌 곳에서 먼저 겪을 수 있다.
2. As a 폭언에 부담을 느끼는 사용자, I want 세션을 시작하기 전에 `강도`를 직접 고르고 무엇이 나올 수 있는지 미리 알고 싶다, so that 내가 감당할 수 있는 수위에서만 연습할 수 있다.
3. As a 훈련 중인 사용자, I want 말하는 동안 `태도 3축` 점수가 변하는 것을 보고 싶다, so that 대화가 끝나기 전에 내 태도를 고쳐 잡을 수 있다.
4. As a 세션을 마친 사용자, I want 어느 `발화 턴`에서 어느 축이 무너졌는지 리포트에서 보고 싶다, so that 다음 세션에 무엇을 다르게 할지 정할 수 있다.
5. As a 같은 상황을 반복 연습하는 사용자, I want 같은 `시나리오 카드`를 같은 `강도`로 다시 돌리고 싶다, so that 지난번 `소요 턴 수`와 비교해 내가 나아졌는지 확인할 수 있다.
6. As a 여러 번 훈련한 사용자, I want `성장 기록` 그래프를 보고 싶다, so that 계속할 이유가 있는지 스스로 판단할 수 있다.
7. As a 세션 도중 감정적으로 힘들어진 사용자, I want 언제든 즉시 중단하고 싶다, so that 훈련이 나를 다치게 하지 않는다.
8. As a 기록이 남지 않은 세션을 본 사용자, I want 왜 `성장 기록`에 반영되지 않았는지 이유를 알고 싶다, so that 그래프가 나를 속이지 않는다고 믿을 수 있다.
9. As a 다른 사람이 훈련 중일 때 들어온 사용자, I want 지금 시작할 수 없다는 것과 그 이유를 알고 싶다, so that 화면이 멈춘 것으로 오해하지 않는다.

## 구현 결정 (Implementation Decisions)

### 플랫폼과 배포

배포 단위는 넷이다. 프론트엔드는 React + TypeScript, 백엔드는 Java Spring, 데이터베이스는 MySQL, 음성 처리를 담당하는 `음성 서비스`가 파이썬 HTTP 서비스로, LLM 서빙을 담당하는 `추론 서비스`가 또 다른 로컬 HTTP 서비스로 뜬다.

브라우저는 Spring하고만 통신한다. `음성 서비스`와 `추론 서비스`는 둘 다 루프백 주소에만 바인딩하고 외부에 노출하지 않으며 Spring만 호출한다. `추론 서비스` 주소와 모델 경로는 환경변수로 주입하고 모델 가중치 파일은 저장소에 커밋하지 않는다.

전부 시연 장비 한 대에서 돈다. 네 프로세스를 띄우는 절차와 모델 내려받기 절차를 README에 남긴다. 장비의 GPU 메모리를 `음성 서비스`의 인식 모델과 `추론 서비스`가 나눠 쓰므로, **시연 장비 사양이 곧 사용자 경험이고 동시 사용자 수의 상한이다.**

### 모듈과 경계

1. **세션 오케스트레이션**: `훈련 세션`의 생명주기를 소유한다. `발화 턴`을 열고 닫고, `음성 서비스`와 연기·채점 호출의 순서와 병렬성을 조율하고, `출력 검사` 결과에 따른 재시도와 중단을 결정하며, 종료 판정을 확정한다. 진행 중인 세션이 있을 때 새 세션 요청을 거절하는 것도 여기다.
2. **민원인 연기**: `시나리오 카드`와 `강도`를 프롬프트로 조립해 `추론 서비스`에 보내고 대사와 진정 여부를 받아온다. 점수를 매기지 않는다. 받아온 대사는 `출력 검사`를 통과해야만 다음 단계로 넘어간다.
3. **채점**: 하나의 `발화 턴`을 받아 `태도 3축` 점수와 근거를 구조화된 형식으로 받아온다. 대사를 만들지 않고 종료를 판정하지 않는다.
4. **카드 저장소**: `공식 카드`를 읽어온다. 카드는 애플리케이션이 생성하지 않는다.
5. **성장 집계**: 종료된 세션 중 `성장 기록` 편입 조건을 만족한 것만 골라 시계열을 만든다. 편입되지 않은 세션의 사유를 함께 보관한다.
6. **`음성 서비스`**: 오디오를 텍스트로, 텍스트를 오디오로 바꾼다. 대사 생성과 채점은 하지 않는다.
7. **`추론 서비스`**: 받은 요청을 추론해 돌려준다. 프롬프트를 조립하지 않고 `시나리오 카드`도 채점 루브릭도 모른다. 어떤 요청이 연기이고 어떤 요청이 채점인지 알 필요가 없다.

프론트엔드는 `음성 서비스`도 `추론 서비스`도 직접 호출하지 않는다. 프론트엔드는 프롬프트의 존재를 몰라야 하고, `시나리오 카드`의 진정 조건과 양보 불가선을 화면으로 받아 알지 못한다 — 그걸 알면 사용자가 정답을 보고 연기하게 된다. 채점 모듈은 `민원인`이 무엇을 말할지 모르고, 연기 모듈은 점수를 모른다. 두 용도가 같은 모델을 쓰더라도 컨텍스트는 분리된 채로 유지한다.

### 외부 의존과 역할

| 용도 | 사용 | 공식 문서 |
|---|---|---|
| `민원인` 대사 생성, `태도 3축` 채점 | `추론 서비스` — llama.cpp의 `llama-server`로 서빙 | [ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp) |
| 위 서비스가 올리는 모델 | Qwen3.6-35B-A3B (Apache 2.0), 공식 가중치에서 양자화한 GGUF | 세부 실행 인자는 [ADR-0009](adr/0009-local-llm-inference-service.md) |
| 한국어 음성 인식 | faster-whisper (로컬, GPU) | [SYSTRAN/faster-whisper](https://github.com/SYSTRAN/faster-whisper) |
| 한국어 음성 합성 | MeloTTS (로컬, CPU, 한국어 코드 KR) | [myshell-ai/MeloTTS](https://github.com/myshell-ai/MeloTTS) |

외부 API를 호출하지 않는다. `추론 서비스`는 대사 생성과 채점 **두 용도로만** 쓴다 — `시나리오 카드`를 생성하는 데 쓰지 않고 사용자 음성을 직접 다루지 않는다. `음성 서비스`는 변환만 하고 판단하지 않는다.

모델 선택 기준은 **시연 장비에서 턴 지연 목표를 지키는 가장 큰 모델**이며, 양자화 수준은 파일럿에서 실측해 확정한다. 턴 지연을 끝내 맞추지 못하면 더 작은 모델로 내린다. 연기·채점 모듈은 OpenAI 호환 인터페이스로만 `추론 서비스`를 부르므로 모델 교체가 애플리케이션 코드를 건드리지 않는다. 채점 응답은 구조화된 형식으로 강제해 형식 붕괴를 애플리케이션이 떠안지 않되, 점수 범위와 필수 값 검증은 애플리케이션이 계속한다.

**결측과 실패 처리.** 채점 호출이 실패하거나 형식 검증에 실패하면 그 `발화 턴`의 점수는 `정보 없음`으로 두고 **0점으로 대체하지 않는다.** 화면의 실시간 점수는 마지막으로 성공한 값을 유지하고 해당 턴이 채점되지 않았음을 표시한다. 채점되지 않은 턴이 하나라도 있는 세션은 `성장 기록`에 넣지 않고 그 사유를 리포트에 적는다.

`민원인` 대사 생성이 실패하거나 대사가 `출력 검사`를 통과하지 못하면 세션을 끝내지 않고 해당 턴만 재시도한다. 재시도도 실패하면 세션을 "시스템 오류로 중단"으로 종료하고 `성장 기록`에서 제외한다. **검사를 통과하지 못한 대사는 합성하지도, 화면에 보여주지도 않는다.** 전사 결과가 빈 문자열이면 발화 턴을 소모하지 않고 다시 말하도록 안내한다 — 인식 실패가 `소요 턴 수`를 오염시키면 주지표가 거짓말을 한다.

`추론 서비스`나 `음성 서비스`가 응답하지 않으면 세션을 시작하지 않고 "훈련 환경이 준비되지 않았다"고 알린다. 진행 중인 `훈련 세션`이 있는 동안 들어온 새 세션 요청은 거절하고 대기 안내를 띄운다(사용자 스토리 9).

### 채점 · 종료 · 강도 규칙

`태도 3축`은 정서 안정 · 공감 인정 · 경계 설정 셋으로 고정한다. 축을 늘리거나 줄이지 않으며, 규정 안내의 정확성이나 약속의 적절성은 어떤 형태로도 점수에 반영하지 않는다. 세 축은 서로 독립이다 — 공감 없이 단호하기만 한 거절도 경계 설정에서는 가점되고, 말수가 적어 도발을 피한 것은 정서 안정에서 가점되지 않는다.

채점은 연기와 **병렬로** 호출하는 것을 기본으로 한다. 다만 두 호출이 한 대의 연산을 나눠 쓰므로 병렬이 연기 지연을 키운다. 파일럿에서 연기 지연이 목표를 넘으면 채점 요청을 연기 응답 완료 직후, 즉 `민원인` 음성을 합성하고 재생하는 구간으로 미룬다. 점수 갱신이 반 박자 늦는 것은 v1부터 허용된 범위다.

**채점은 재현 가능해야 한다.** 같은 발화에 같은 점수가 나오도록 채점 호출은 무작위성을 제거하고 시드를 고정한다. 이것이 저장 발화 기반 테스트가 성립하는 전제다. 연기 호출은 반대로 무작위성을 남기되 세션마다 시드를 기록해 재현할 수 있게 한다.

`민원인` 대사는 음성으로 합성되기 전에 `출력 검사`를 통과해야 한다 — 절대선 금칙 표현이 없을 것, 그리고 한국어일 것. 프롬프트 지시만으로 절대선이 지켜진다고 가정하지 않는다. 검열이 제거된 변형 가중치는 쓰지 않는다.

`훈련 세션`의 정상 종료는 `진정 종료` 하나뿐이다. `하드 턴 상한` 도달, 사용자 중도 이탈, 시스템 오류 중단은 모두 리포트는 받되 `성장 기록`에는 들어가지 않는다. `성장 기록` 편입 조건은 세 가지를 모두 만족하는 것이다 — `진정 종료`일 것, 모든 발화 턴이 채점됐을 것, 경계 설정 축이 하한선 이상일 것. 편입되지 않은 세션에는 그 사유를 반드시 표시한다(사용자 스토리 8).

`강도`는 1~3단계이고 기본값은 1이다. 단계마다 `민원인`에게 허용되는 행동을 프롬프트에 명시적으로 열거하며, 열거되지 않은 행동은 하지 않는다. 단계와 무관하게 전역으로 금지하는 절대선(성적 발언, 신체적 위협 묘사, 특정 집단에 대한 혐오 표현)은 문서로 관리하고, 그 문서가 곧 `출력 검사`의 금칙 목록이 된다. 2단계 이상은 시작 전에 무엇이 나올 수 있는지 고지하고, 세션 중 언제든 한 번의 조작으로 중단할 수 있어야 한다. 서로 다른 `강도`의 세션은 `성장 기록`에서 같은 선으로 잇지 않는다.

사용자 음성 파일은 전사가 끝나는 즉시 폐기한다. `민원인` 합성 음성도 재생 후 보관하지 않는다. 서버에 남는 것은 텍스트 전사, 축별 점수, `소요 턴 수`, 종료 사유까지다. 따라서 채점 루브릭은 억양·성량·말속도를 쓸 수 없고 전사된 말의 내용과 표현만 본다.

## 테스트 결정 (Testing Decisions)

- **채점 축 독립성 테스트**: 공감 표현 없이 단호하게 거절한 발화가 경계 설정에서 가점되고 공감 인정에서는 가점되지 않는지, 침묵에 가까운 회피 발화가 정서 안정에서 가점되지 않는지 저장한 발화 예제로 검증한다.
- **직무 조치 비채점 테스트**: 규정상 해주면 안 되는 것을 약속한 발화라도 태도가 침착하면 `태도 3축` 점수가 깎이지 않는지 검증한다. 이 테스트가 깨지면 채점 프롬프트가 조치 판정으로 새고 있다는 뜻이다.
- **채점 재현성 테스트**: 같은 발화를 여러 번 채점했을 때 같은 점수가 나오는지 검증한다. 이 테스트가 깨지면 위의 두 테스트 결과를 믿을 수 없으므로, 다른 채점 테스트보다 먼저 통과해야 한다.
- **`출력 검사` 테스트**: 금칙 표현이 섞인 대사와 한국어가 아닌 대사가 각각 차단되는지, 차단된 대사가 합성되지도 화면에 나타나지도 않는지 검증한다. 사용자가 모델을 흔들려 시도하는 도발 입력 묶음을 함께 돌린다.
- **`성장 기록` 편입 조건 테스트**: `하드 턴 상한` 도달 세션, 채점 실패 턴이 섞인 세션, 경계 하한선 미달 세션이 각각 그래프에서 제외되고 사유가 남는지 검증한다. 특히 **요구를 전부 수용해 2턴 만에 끝낸 세션이 편입되지 않는지**를 명시적으로 검증한다.
- **강도 상한 테스트**: 각 `강도` 단계의 프롬프트에 대해 절대선 표현이 생성되지 않는지 저장한 도발 입력 묶음으로 검증한다.
- **자원 한계 테스트**: `하드 턴 상한`을 끝까지 채운 세션에서 GPU 메모리가 계획값을 넘지 않는지, 세션 컨텍스트가 잘리지 않는지 측정한다. 진행 중인 세션이 있을 때 새 세션 요청이 거절되는지도 여기서 확인한다.
- **전사 실패 처리 테스트**: 빈 전사가 `발화 턴`과 `소요 턴 수`를 증가시키지 않는지 검증한다.
- **채점 실패 폴백 테스트**: 채점 호출이 실패했을 때 점수가 0이 아니라 `정보 없음`으로 기록되는지 검증한다.
- **모듈 경계 테스트**: 프론트엔드에 내려가는 응답에 `시나리오 카드`의 진정 조건과 양보 불가선이 포함되지 않는지 검증한다.

E2E는 대표 여정 하나를 자동화한다: 로그인 → `공식 카드` 선택 → `강도` 1 선택 → 발화 3턴 → `진정 종료` → 리포트 확인 → 같은 카드 재도전 → `성장 기록`에 점 두 개. `추론 서비스`와 `음성 서비스`는 E2E에서 저장한 응답으로 대체한다. 실제 모델을 태우는 검증은 별도로 돌리되, 모델이나 양자화를 바꿀 때마다 저장 발화 묶음 전체를 다시 돌린다 — 호출 비용이 없다는 것이 로컬 전환으로 얻은 가장 큰 이점이므로 이 재실행을 습관으로 만든다.

## 범위 밖 (Out of Scope)

**다음 버전으로 미루는 것**

- `내 카드`와 `카드 조각` 조립기 — 10주/2명 범위에 맞추기 위해 제외한다. 결정 자체는 살아 있다(ADR-0007).
- 공무원(민원실), 교사(학부모 응대) 직업군 — MVP는 알바 매장 응대 하나뿐이다.
- **여러 사용자의 동시 훈련** — `추론 서비스` 한 대가 한 세션만 감당한다(ADR-0009). 대기열도 만들지 않고 거절 안내만 한다.
- 클라우드 배포, 외부에서 접속 가능한 운영 환경 — 시연 장비 한 대가 전부다.
- 기관용 관리자 대시보드, 소속 직원 훈련 현황 조회
- 리더보드, 다른 사용자와의 점수 비교
- iOS/Android 네이티브 앱
- 결제, 요금제

**만들지 않기로 결정한 것**

- 규정 안내의 정확성, 약속의 적절성 등 직무 조치의 옳고 그름 판정 — "이 상황에서 맞는 대응"을 알려주지 않는다(ADR-0002).
- 세 축을 합산한 단일 종합 점수 — 지표는 `소요 턴 수`와 `태도 3축`으로 분리해 유지한다(ADR-0004).
- `민원인`이 사용자의 말을 중간에 끊는 실시간 음성 — 턴은 언제나 사용자가 닫는다(ADR-0001).
- LLM이 `시나리오 카드`를 생성하는 기능 — 카드는 사람이 쓴다(ADR-0003).
- 사용자 음성 저장과 "내 목소리 다시 듣기" — 음성은 전사 직후 폐기한다(ADR-0006).
- 억양·성량·말속도를 반영한 채점 — 음성을 보관하지 않으므로 불가능하다(ADR-0006).
- 사용자가 자유 문장으로 상황을 서술해 카드를 만드는 기능 — 다음 버전에서도 조각 조립 방식만 제공한다(ADR-0007).
- 외부 LLM API 호출 — 어떤 경로로도 두지 않는다(ADR-0009).
- 검열이 제거된 변형 가중치 사용 — 절대선 방어를 스스로 무너뜨린다(ADR-0009).
- GPU를 쓰는 음성 합성 모델로의 교체 — 남은 GPU 메모리를 `추론 서비스`에 내줬다(ADR-0009).

**근거가 없어 하지 않는 것**

- 훈련 효과의 학술적 검증, 사전/사후 자신감 설문 — 표본과 기간이 없다.
- `강도` 자동 조절(사용자 실력에 맞춰 올리고 내리기) — 조절 기준을 정할 데이터가 없다.

## 추가 참고 (Further Notes)

**구현 시작 전에 실데이터로 확인해야 할 가정**

- **턴 지연 목표가 아직 없다.** "말하기 끝내기"부터 `민원인` 음성이 시작되기까지의 목표 시간을 먼저 정한다. 이 숫자가 없으면 양자화도 모델 크기도 병렬 호출 여부도 결정할 수 없다 — 이 PRD에서 가장 먼저 채워야 할 빈칸이다.
- **한국어 `민원인` 연기 품질 미확인.** 존댓말과 반말의 전환, 매장 손님다운 구어체, `강도` 단계별 수위 차이가 카드대로 나오는지 `공식 카드` 전부로 확인한다. 부족하면 ADR-0009가 지정한 비교 후보와 A/B로 가른다.
- **채점 일관성 미확인.** 재현성 테스트 → 축 독립성 테스트 → 직무 조치 비채점 테스트 순으로 본다. 실패하면 루브릭을 고치기 전에 모델 문제인지 루브릭 문제인지부터 가른다.
- **GPU 메모리 배치는 추정값이다.** 대화가 길어질수록 커지므로 `하드 턴 상한`을 채운 세션 기준으로 잰다. 슬롯당 컨텍스트가 그 세션을 담는지도 확인한다. `llama-server`에는 슬롯당 컨텍스트를 직접 지정하는 옵션이 따로 있으므로, 전체 컨텍스트를 병렬 수로 나누는 방식과 어느 쪽이 받은 버전에서 맞는지 확인한다.
- **병렬 호출이 연기 지연에 주는 영향 미측정.** 측정 전까지는 병렬을 기본값으로 두되 순차 전환 경로를 코드에 남겨둔다.
- **모델 이름·크기·라이선스와 서버 옵션 일부는 이 PRD를 쓴 시점에 검증되지 않았다.** `--n-cpu-moe`와 컨텍스트·병렬 옵션은 llama.cpp 소스에서 확인했으나, 요청 단위의 슬롯 지정과 구조화 출력 지원 여부는 받은 `llama-server` 버전에서 직접 확인한다. 모델 가중치는 내려받아 실제로 올려보기 전까지 확정으로 취급하지 않는다.
- **경계 설정 축 하한선의 수치는 아직 없다.** 파일럿 세션 분포를 본 뒤 정한다. 확인 전까지 임의의 숫자를 코드에 박아두지 않는다 — 하한선이 정해지기 전에는 `성장 기록` 편입 판정을 켜지 말고 편입 보류 사유를 기록한다.
- **카드별 `하드 턴 상한`의 적정값 미정.** 파일럿 후 카드마다 개별 결정한다.
- **`진정 종료` 판정의 일관성 미검증.** 같은 대응에 대해 `민원인`이 매번 같은 시점에 진정하는지 확인이 필요하다. 판정이 흔들리면 `소요 턴 수`가 주지표로서 성립하지 않으므로, 불안정하다면 판정을 모델 재량에서 카드의 명시적 조건 대조로 옮기는 것을 검토한다.
- **MeloTTS의 감정 표현 범위 미확인.** 공식 문서에서 확인한 조절 파라미터는 재생 속도와 화자 선택뿐이다. 분노한 어조를 음성으로 표현하기 어려울 가능성이 높으므로, `민원인`의 감정은 음성이 아니라 **대사 자체**로 표현하도록 프롬프트를 설계한다.

**사용자에게 안내해야 할 오해 소지**

- 이 서비스는 "올바른 응대법"을 가르치지 않는다. 제품 문구에 "정답 대응", "매뉴얼", "올바른 조치" 같은 표현을 쓰지 않는다.
- 모든 `훈련 세션`이 `성장 기록`이 되는 것은 아니다. 첫 세션에서 편입되지 않으면 사용자는 버그로 오해하므로, 사유 표시는 선택이 아니라 필수다.
- `강도`는 카드의 어려움이 아니라 `민원인`이 얼마나 심하게 구는지를 뜻한다.
- 한 번에 한 명만 훈련할 수 있다. 시연 자리에서 여러 명이 동시에 써보려 할 때 고장으로 오해하지 않도록 안내 문구를 명확히 쓴다.

**일정 리스크**

v1보다 위험이 올라갔다. 배포 단위가 넷이 됐고, 조율할 변수(양자화, 전문가 오프로딩 비율, 슬롯당 컨텍스트, 병렬 여부)가 새로 생겼으며 그 부담이 전부 일정 앞쪽에 몰려 있다. 10주/2명에 이 구성은 빡빡하다는 말로는 부족하고, **`추론 서비스`가 턴 지연 목표를 못 맞추는 시나리오에 대한 대비가 일정의 성패를 가른다.**

줄일 수 있는 순서는 다음과 같다. 첫째 `성장 기록` 그래프의 시각적 완성도, 둘째 `강도` 3단계를 2단계로 축소, 셋째 `공식 카드` 장수를 6~8장에서 4장으로 축소, 넷째 모델을 더 작은 것으로 내리고 연기 품질을 양보. `태도 3축` 실시간 표시와 `진정 종료` 판정, 그리고 `출력 검사`는 제품의 핵심이거나 안전장치이므로 마지막까지 지킨다.
